# isthereaburnban.com rebuild — research notes (opus seat, emphasis: SEO + agent interface)
Started 2026-11-23 18:24 CST.

## Takeaway
Build one static Astro page per county (about 3,100) plus state pages, each showing the current status, "last checked", "status changed on", history, the official source link and neighbouring counties. Google no longer shows SpecialAnnouncement or FAQ rich results, so use plain HTML, BreadcrumbList and one Dataset. Make lastmod honest. Treat ZIPs as a lookup that redirects to the county page; do not build indexed ZIP pages.
For agents, one Worker should serve `/api/status?zip=|lat,lon|county=` as JSON, `/openapi.json`, a small `llms.txt`, and a stateless remote MCP (`createMcpHandler`) listed in the official MCP Registry as `com.isthereaburnban/mcp`. None of the 5 competitors I checked has an API or MCP.
Data: OK (ArcGIS), TX (UTF-16 txt/RSS), IN, FL and MS are live machine-readable feeds; competitors already cover 12 to 47 states, so the field is crowded and the agent API is where this site can stand out.

## Cited findings

### SEO — Google guidance (fetched 2026-11-23 via curl, read in full unless noted)
- **Scaled content abuse** = "many pages are generated for the primary purpose of manipulating search rankings and not helping users… no matter how it's created." Examples include "Scraping feeds… to generate many pages… where little value is provided to users" and "Stitching or combining content from different web pages without adding value." https://developers.google.com/search/docs/essentials/spam-policies (page "Last updated 2026-11-23"). Read in full.
- **Doorway abuse** examples: "Having multiple domain names or pages targeted at specific regions or cities that funnel users to one page" and "Creating substantially similar pages that are closer to search results than a clearly defined, browseable hierarchy." Same URL. Read in full.
- **SpecialAnnouncement is dead in Google**: "Simplifying the search results page" (2025-06-12) lists Special Announcement among types "phased out"; "This update won't affect how pages are ranked… use… outside of Google Search… is not affected." https://developers.google.com/search/blog/2025/06/simplifying-search-results . Docs removed 2025-09-09 ("no longer shown in Google Search results"). The old docs URL now redirects to What's New. https://developers.google.com/search/updates — read in part.
- **FAQPage rich result is dead**: What's New, 2026-05-08 "This feature will no longer appear in Google Search starting May 7, 2026"; docs removed later ("no longer shown in Google Search results, as announced in the changelog entry in May 2026"). https://developers.google.com/search/updates — read in part.
- **llms.txt and Google**: What's New 2026-06-15: llms.txt files "aren't needed for Google Search (and won't negatively or positively impact your visibility or rankings), it's fine if you want to maintain these files for other services." Same URL.
- **AI Overviews/AI Mode**: "You don't need to create new machine readable files, AI text files, or markup to appear in these features. There's also no special schema.org structured data that you need to add." Also: "Making sure your structured data matches the visible text on the page." https://developers.google.com/search/docs/appearance/ai-features . Read in full.
- **Sitemaps**: "All formats limit a single sitemap to 50MB (uncompressed) or 50,000 URLs"; use a sitemap index. "Google ignores <priority> and <changefreq> values. Google uses the <lastmod> value if it's consistently and verifiably… accurate." Significant update = "main content, the structured data, or links." https://developers.google.com/search/docs/crawling-indexing/sitemaps/build-sitemap (Last updated 2026-07-08). Read in full.
- **Sitemap ping removed** (2023-06-26): ping endpoint returns 404; lastmod is "a signal for scheduling crawls"; if lastmod lies "eventually we're not going to believe you." Submit via robots.txt and Search Console. https://developers.google.com/search/blog/2023/06/sitemaps-lastmod-ping . Read in full.

### Agent interface
- **Remote MCP on Cloudflare Workers is now stateless**: "`createMcpHandler` from `agents/mcp/server` serves an MCP SDK v2 server from a Worker. The handler is stateless: it builds a fresh server for every request, so you do not need a Durable Object, protocol session, or WebSocket." `McpAgent` is deprecated. Install: `npm i agents @modelcontextprotocol/server@2.3.1 zod`; the example registers a tool with `server.registerTool(name, {description, inputSchema: z.object(...)}, handler)`. https://developers.cloudflare.com/agents/model-context-protocol/apis/handler-api/ (fetched as index.md 2026-11-23; read in part, about the first 3.5k chars). A search summary says Agents SDK v0.20.0 deprecated McpAgent to track MCP spec 2026-07-28, which drops the initialize handshake and Mcp-Session-Id (search summary only, citing bex.co, 2026-09-13).
- **Official MCP Registry** (still "in preview… data resets may occur"): the API works without a key, e.g. `curl https://registry.modelcontextprotocol.io/v0/servers?search=wildfire` returned com.olyport/wildfire (NIFC incidents), com.daedalmap/wildfires and io.github.vria-consulting/kanari-wildfires. Searches for "burn" and "fire" returned **no burn-ban server**. Domain-based auth gives the name `com.isthereaburnban/*` and needs a DNS TXT record on the **apex** (`v=MCPv1; k=ed25519; p=…`); GitHub auth gives `io.github.<user>/*`. https://raw.githubusercontent.com/modelcontextprotocol/registry/main/docs/modelcontextprotocol-io/authentication.mdx (read in part).
- **llms.txt usage evidence** (search summary only; secondary SEO-industry studies, not read in full): an Ahrefs study (2026-06-15) of 137,210 domains found that of about 38k valid llms.txt files "about 1,100 received any traffic at all"; several single-site log studies saw zero AI-crawler requests; one exception (SEO Dima, 19 sites) saw reads when llms.txt was linked from pages; Mintlify reports that llms.txt helps coding agents on docs sites. Together with Google's own statement above: llms.txt is cheap to add but has little effect. https://auxfirst.com/news/llms-txt-evidence.html , https://seodima.com/notes/what-ai-crawlers-do-with-llms-txt/
- **What assistants actually fetch**: ChatGPT-User, Claude-User and Perplexity-User are user-triggered fetchers that read ordinary HTML pages when a user asks; OAI-SearchBot and Claude-SearchBot index pages for in-chat search. Search summary says Claude-User honors robots.txt and ChatGPT-User/Perplexity-User may not. Search summary only (third-party guides); primary pages not read.
- **Cloudflare Markdown for Agents**: returns Markdown at the edge when the request has `Accept: text/markdown` and adds `Content-Signal: ai-train=yes, search=yes, ai-input=yes` unless the origin sets its own. "available to Pro, Business and Enterprise plans… at no cost", **so it is not on Free**. https://developers.cloudflare.com/fundamentals/reference/markdown-for-agents/ (read in part).
- **Cloudflare managed robots.txt / AI Crawl Control**: Cloudflare prepends managed directives only when "Enable Bot Preference Sync" is on and a Search, Agent or Training policy is set to Block. AI Crawl Control is "Available on all plans." https://developers.cloudflare.com/bots/additional-configurations/managed-robots-txt/ (read in part). Inference: after moving the zone, check these settings so Cloudflare doesn't block ChatGPT-User or Claude-User, which defeats the agent goal.

## Inferences (mine)
- **The page model that avoids scaled content and doorway abuse**: each county page answers a real, distinct question with a distinct, changing fact (the status) plus value the source does not offer. That means status history, "status changed on", real map neighbours, the county's own contact page, scope notes (city vs. county, as burnbanfinder does), and the official order or resolution link (the OK layer has attachments). A clear hierarchy (home → state → county) avoids the "closer to search results than a browseable hierarchy" pattern. Don't create keyword-variant pages ("burn ban near me", "…today", "…in my area") as burnbancheck does.
- **ZIP**: about 10,186 rows in the Census 2020 ZCTA→county relationship file are ZCTAs listed more than once (they cross county lines; my awk count, roughly). So `/api/status?zip=` must return **all** counties a ZIP touches, with an "ambiguous" flag, and suggest lat/lon for precision. ZIP pages would be near-duplicates of county pages, so don't index them: either redirect a ZIP to its county or render it with noindex plus a canonical to the county. File: https://www2.census.gov/geo/docs/maps-data/data/rel2020/zcta520/tab20_zcta520_county20_natl.txt (200, 6.8 MB, Last-Modified 2021-12-09; public domain as a Census product).
- **Freshness**: Google uses lastmod only when it is accurate, so set a county's `<lastmod>` to the time its **status changed**, not the build time. burnbanradar stamps 3,046 of 3,057 URLs with today's date, which Google says it will learn to ignore. Show "Last checked" and "Status since" visibly on the page, and add `dateModified` in WebPage JSON-LD to match the status change. Rebuild static pages on a cron (e.g. hourly), or serve county pages from the Worker with KV and a short edge cache. Astro on Cloudflare can mix prerendered and on-demand pages, so either works. Plan for about 3,200 URLs; one sitemap holds 50k, but split per state so Search Console reports per state.
- **Structured data worth using**: BreadcrumbList (still a rich result), WebPage with dateModified, Organization/WebSite on home, and one Dataset (+ DataDownload for `/api/bans.json` and CSV) on a /data page for Google Dataset Search. Skip FAQPage and SpecialAnnouncement for Google. SpecialAnnouncement has no effect on Google ranking; other consumers might read it, but that is unproven.
- **Agent API shape** (judgement): use GET only with no auth, cacheable at the edge, CORS `*`. `GET /api/status?zip=74103 | lat=&lon= | state=OK&county=Tulsa` returns `{query, results:[{state, county, fips, status: "ban"|"none"|"restricted"|"unknown", label, since, last_checked, source_name, source_url, official_page_url}], ambiguous, disclaimer}`. Add `GET /api/bans.json` (all active), `/api/states.json` (coverage list with source and cadence), `?format=text` for plain one-line answers, and `/openapi.json` (OpenAPI 3.1). Always return `unknown` for uncovered states, never "none". The MCP server exposes the same three functions as tools (`check_burn_ban(zip|lat,lon|county)`, `list_active_bans(state?)`, `coverage()`) and calls the same code. Remote MCP clients (Claude, ChatGPT apps) connect through the registry or a URL; framework tool-calling agents use OpenAPI or plain GET; chat assistants mostly just fetch the HTML page. So the HTML county page is still the most-used "agent interface".
- **llms.txt**: a 20-line file that points to the API, OpenAPI and MCP URL. Google says it is harmless and log studies show it is rarely fetched, so it costs little and does little. Link it from pages and the API docs, since one log study found reads only when it was linked.
- **robots**: allow search and user-triggered AI fetchers (OAI-SearchBot, ChatGPT-User, Claude-SearchBot, Claude-User, PerplexityBot). Blocking training crawlers is optional, as burndates does. After moving DNS to Cloudflare, confirm AI Crawl Control and managed robots are not blocking these bots.
- **Alerts** (outside my emphasis): competitors already offer per-county email alerts on status change (burnbanradar). A Cron Trigger diffs each poll against the last state in KV, then sends email and push (Web Push with VAPID from a Worker) to subscribers of that county's FIPS. Since the status changes rarely, the cost is low.
- **Astro**: worth it. Thousands of static pages from one template, island-only JS for the map (load MapLibre only on /map), and an official Cloudflare adapter. Other seats are verifying the stack.
