# Testing burn ban notifications without spamming subscribers

2026-11-23 · Resend, Web Push, and the Cloudflare Worker

## Short answer

Run test sends through the deployed notifier and limit the audience to opted-in staff devices or confirmed staff email subscriptions. Preview the real county audience using the same selection code, then use a real browser on the public origin and a controlled inbox to verify what recipients actually see. Resend’s simulator covers accepted requests and simulated provider outcomes without mailing anyone. An opt-in daily push helps catch delivery regressions between real bans. Provider acceptance and a small staff cohort leave inbox placement, device diversity, and large fan-out to verify separately.

## What we chose and why

- Keep Resend and the existing Web Push transport. Cron alerts and the dashboard share recipient selection, push encryption, email composition, and delivery logging. Simulated county transitions are labeled and restricted to the test cohort. A simulator address is chosen from a fixed server-side list. The browser gets the same root service worker and VAPID key as the public site.
- Compute the full county audience on demand, page through masked recipients, and show the notice. A real broadcast reports fresh county data, requires the county name and a matching preview, and uses conservative manual rate and recipient caps. The stop is checked before dispatch. The log records acceptance, errors, and gone endpoints without recording raw addresses or push capabilities.
- Run an optional push canary daily on devices that explicitly opt in. Keep it off by default to avoid recurring noise. A receiving device or controlled inbox is still needed to verify rendering. Revisit the fan-out design if real audiences routinely exceed the Worker budget or the logs show provider throttling.
